## Working conventions

- Use pnpm workspaces, root scripts and strict TypeScript. Keep boundaries explicit; avoid premature abstractions.
- Preserve the approved responsive visual design and semantic accessible HTML.
- Preserve prerendering of the landing. The approved Node endpoint requires a server; do not claim a static file deployment supports lead capture.
- Validate untrusted input server-side. Never expose server configuration, credentials, personal data in logs or analytics, or public read/export endpoints.
- Maintain privacy text/version, retention and consent audit together. No vendor without approval. Do not commit database files, exports, `.env`, or real lead fixtures.
- Keep product, architecture and implementation documentation consistent; mark old milestone records as historical.
- Do not modify or deploy Orbia infrastructure. This milestone prepares Docker/Compose/GHCR and operations; actual deployment and provisioning are outside scope.
- Before adding a dependency, confirm existing capabilities are insufficient.
- The API loads `@whiteoven/pizza-pricing` and `@whiteoven/contracts` as TypeScript source (Node strips the types; ADR 0018): keep those packages to erasable syntax and update the API `Dockerfile` when the API depends on another workspace package.
- Do not claim checks passed unless they completed successfully.

## Commands

- `pnpm dev`: start local Astro with app `.env`.
- `pnpm build` / `pnpm start`: build and serve through the guarded Node launcher (`pnpm start`), preserving trusted request identity and HTTP limits.
- `pnpm typecheck` / `pnpm test`: run in every workspace package that defines them (`pnpm -r --if-present`). `pnpm test` covers landing (pizza, lead contract, endpoint, persistence, backups), API (config, logging, errors, OpenAPI, startup, database roles and migrations, tenant isolation) and `tests/deployment/ops.test.mjs` (ops and GHCR script decisions against a recording docker/gh/curl double).
- `pnpm test:e2e`: build and test desktop/mobile with synthetic local capture configuration.
- `pnpm check`: format, lint, typecheck.
- `pnpm admin:dev`: Angular panel on `localhost:4200`, proxying `/v1` to the API on `127.0.0.1:3000` (set `API_ADMIN_ORIGINS=http://localhost:4200` in `apps/api/.env`). `pnpm test:e2e:admin` runs its Playwright tests against a throwaway PostgreSQL database and needs `TEST_DATABASE_OWNER_URL`.
- `WHITEOVEN_TENANT=pizzaria-centro pnpm mobile:start`: Expo dev server for one store's manifest (`WHITEOVEN_API_URL` defaults to `http://localhost:3000`; HTTPS elsewhere). Keep app logic in modules without React Native imports so `node --test` covers it; never store tokens or personal data in the brand cache. Load the store through `createStoreRefresher` (one load at a time; a disposed load writes nothing), and never show the store as open without a valid `/status` answer (ADR 0020). The builder never applies a PB rule of its own: every choice goes through `evaluatePizza`, and halves are described from the normalized configuration (ADR 0021). Do not call `validatePizzaCatalog` at runtime in the app (it uses `structuredClone`, which Hermes does not guarantee); keep it in tests. Respect reduced motion with `transitionMs`/`useReducedMotion`. The public image route must serve only images the public menu or the brand shows. Decide the screen only through `screenFor` (a store confirmed unavailable wins over the builder; offline is not unavailable), keep a menu that failed to reload marked `stale` and say so on the menu and in the builder, and change sizes only through `changeSize` (block unpriced flavors and lossy halves, confirm dropped crust/extras).
- M5.3 commerce: use `createCommerceModel` for serialized actions and durable confirmations; persist the exact body/key before POST, keep ambiguous results locked to the original customer, and never retry an expired key as a new order. Refresh tokens and commercial state use SecureStore, scoped by API + slug; access tokens stay in memory. Manifest privacy notices are demonstration-only until M7.2. `pnpm test:e2e:mobile` exercises the app controller against real API/PostgreSQL with synthetic data.
- M5.4 customer orders: list and detail reads use the authenticated customer id plus tenant RLS and `Cache-Control: no-store`; never expose staff notes or internal incident text. Poll only while the order detail is visible and the app is active (20 seconds). Reorder from immutable snapshots through `validatePizzaConfiguration` and `evaluatePizza` against the current public catalog; current price must still be quoted at checkout. No route tracking or push in this milestone.
- M5.6 store builds: every manifest has `{slug}-preview` and `{slug}-production` profiles in `apps/mobile/eas.json` that only set `WHITEOVEN_TENANT`; `WHITEOVEN_API_URL` lives in each EAS project's environments, never in the repository, and no credential or credential path enters `eas.json`. A store build refuses a demonstration privacy text, a transparent icon or a missing `easProjectId`/`expoOwner` (`pnpm mobile:release-check <slug> <preview|store> [--platform] [--submit] [--eas]`). Read `eas.json` only through `@expo/eas-json` (`apps/mobile/scripts/eas-profiles.ts`), never with a hand-written `extends` resolver. Builds run only through the manual `Mobile build` workflow or an operator; never trigger one without task authorization.
- M6.1 plans: periods are written only by the `whiteoven_change_tenant_plan` SECURITY DEFINER function (the app role can only read them); never update a period that already took effect, never let an ACTIVE tenant lose its current plan, and copy plan values into the period instead of reading the catalog later.
- M6.2 billing ledger: `billing_entries` is written only by `whiteoven_record_order_completion` and `whiteoven_reverse_billing_entry` (the app role can only read it) and is never updated or deleted; a correction is a new `ORDER_REVERSED` row with negated components, the original plan snapshot and a reason code, never free text or personal data.
- `pnpm api:dev`: build and start the API on `127.0.0.1:3000` with `apps/api/.env` if present. `docker compose -f compose.dev.yaml up --build api` runs it in a container.
- API conventions: configuration only through `loadConfig` (invalid values must stop the start); throw `ApiError` with a stable code; never log personal data, query strings, headers or bodies.
- `pnpm db:up` / `pnpm api:migrate`: start dev PostgreSQL; apply migrations as `whiteoven_owner` from `apps/api/.env.migrate`. The API runs only as `whiteoven_app` and never gets owner credentials or runs DDL; schema changes are new entries in `apps/api/src/database/migrations/index.ts` (forward-only, names never change).
- Tenant tables: the migration runs `tenantIsolationSql(table)`, declares `tenant_id uuid not null references tenants (id)`, `unique (tenant_id, id)` and composite FKs; the entity declares `filters: tenantFilters`; services reach tenant data only through `TenantTransactions.run`. Add the table and its routes to `apps/api/test/tenant-isolation.test.ts` (matrix and coverage) in the same PR. The tenant never comes from a header, body or query.
- Catalog tables that feed the public menu also get the per-statement `whiteoven_bump_catalog_version()` trigger and the `BEFORE UPDATE OF tenant_id` `whiteoven_guard_catalog_tenant()` trigger in their migration, so the per-tenant menu cache is invalidated on every instance (ADR 0011).
- Every route declares its access: `@PublicRoute()`, `@StoreTenant()`, `@StaffRoute()`, `@AdminRoute(...roles)` or `@PlatformRoute()`. The global `RouteAccessGuard` refuses undeclared routes and `staff-auth.test.ts` fails on them. Staff routes inside a store use `@AdminRoute`, which binds the `TenantContext` from the verified token and joins the isolation matrix.
- API integration tests need `TEST_DATABASE_OWNER_URL` (see README); without it they are skipped locally and fail in CI. Never mock PostgreSQL for isolation or privilege tests.
- `node --experimental-strip-types tests/deployment/containers.mjs`: build and test isolated Docker resources with synthetic data only.
- `bash ops/whiteoven.sh`: deployment operations; never execute against real environments without task authorization.
- `bash ops/api-backup.sh`: API backup/restore (PostgreSQL + images, ADR 0029, [runbook](docs/operations/api-backup-restore.md)); never execute against real environments without task authorization. A restore always reapplies customer deletions with `ops/postgres/reapply-customer-erasures.sql`: when `deleteAccount` erases something new, or a new table references `customers`, update that file and `apps/api/test/backup-erasures.test.ts` in the same PR. Deletions come only from a source that proves continuity (same `database_lineage`, intact `customer_erasures` chain containing the backup's head); never add a bypass for `ERASURES_MISSING`, `ERASURES_LEDGER_INVALID` or `ERASURES_STALE`, and never update or delete `customer_erasures` rows. New global tables go in `GLOBAL_TABLES` (`tenant-isolation-sql.ts`). Images must be published complete (temp file, fsync, rename) before the metadata commits and stay append-only after commit, or the backup order (dump, then images) must be revisited. Restore operations live in `.ops-state/api-restores/<op>` (`restore-status`, `restore-rollback`, `restore-cleanup`); only resources carrying the operation's mark may be dropped or removed. `node tests/deployment/api-restore-drill.mjs` runs the restore drill (injected failures, kills, invalid ledgers, concurrent uploads) in an isolated Compose with synthetic data.
- `pnpm leads`: local operations; see README and capture runbook. Deletion/export of real leads requires task authorization.
